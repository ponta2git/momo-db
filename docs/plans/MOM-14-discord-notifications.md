# MOM-14 Discord 通知の共有永続化・DB リファクタ実施計画

2026-09-09 承認の実施計画。実装・検証と、メンテナンス中の導入順序を定める。

実装した物理名、payload v1、DB 関数と consumer の接続方法は [共有通知契約](../discord-notifications.md) を参照する。

[MOM-14](https://linear.app/ponta/issue/MOM-14) の目的は、Summit が受け付けた OCR 完了通知（A）・分析完了通知（B）について、固定内容、重複防止、取消、配送と回復の状態を共有 DB に永続化することである。既存の開催アンケートも共通の通知・配送基盤へ移し、業務ごとの振る舞いを明示する。

要件の参照先は [通知要件仕様](https://linear.app/ponta/document/discord通知-要件仕様ocr完了分析完了-59da567fe5ba) と [採用方式・連携契約](https://linear.app/ponta/document/discord通知の採用方式連携契約-7830c9e66f29)。DB 変更の規範は [development.md](../development.md) に集約する。本書は実施範囲・合意事項・検証計画を記載し、規範を重複定義しない。

今回、次の方針で合意している。

| 項目 | 決定 |
| --- | --- |
| 切替方式 | 利用者へのメンテナンス通知と全 writer 停止を前提に、DB と対応 consumer を一括で切り替える。無停止互換性のためだけの旧新併用は不要 |
| 共通化 | `discord_outbox` の改名・再構成を含め、既存アンケートと A/B の通知・配送を共通化する |
| 必ず保全するデータ | 既存の開催履歴、参加者履歴、試合・順位・事件・メモ等の記録と参照関係 |
| 終了済み Session・回答 | 移行時に整理できる。開催履歴との対応が不明なものも、特別な保全対象にしない |
| 不明な過去の開催 | Session の状態や日時から開催履歴を新設・紐付け直す補完は行わない。現存する開催履歴を維持する |
| 本文・配送詳細の保持 | `DELIVERED` は終端から 7 日、`FAILED` / `CANCELLED` は終端から 30 日。配送待ち・処理中は整理しない |
| 重複防止の保持 | 通知 ID、元ジョブ等の一意性、内容照合情報、終端状態を期限なしで残す。本文整理後は旧本文の参照・再送をしない |
| 分割配送中の取消 | 配送済み部分は残し、送信開始前の残りを取り消す。開始済みの部分は届く場合がある。再 ON でも残りを復帰させない |

**調査から実装へ引き継ぐ事実**

現行の `held_events.session_id` は nullable だが、Session 削除時に `CASCADE` する。さらに参加者履歴は開催履歴から `CASCADE`、試合・下書きは開催履歴に対して `RESTRICT` である。Session を整理する前に、開催履歴の Session 参照を `ON DELETE SET NULL` へ変更する。開催 ID・日時・参加者履歴と試合の参照を維持し、Session 由来の開催を削除しない。`TRUNCATE ... CASCADE` は使用しない。

momo-result の開催履歴取得と試合参照は `held_events` を使い、アンケート Session に依存していない。Session を持たない開催も既に存在する。したがって、Session との関連を外しても、開催履歴そのものを保全すれば試合記録との整合を維持できる。

調査時点の Session はすべて過去の終了状態で、既存 outbox に未配送・claim 中の行はなかった。この結果は切替時点を保証しないため、メンテナンス直前に再確認する。新たに進行中となった Session や未配送行は、終了済みデータの整理に巻き込まず、新構造に移す。未配送・再試行対象の通知が参照する Session は、終了状態でも整理対象から外す。

既存 Summit では、リマインド配送後に Session 完了・開催履歴・参加者履歴を同じ業務 transaction で確定する。通知テーブルの共通化後もこの動作を維持する。また、起動時の FAILED・後続 CANCELLED の復帰はアンケート固有の処理であり、A/B に適用しない。

**保存構造と責務**

以下を実装の基準とする。物理名は既存命名との整合を確認して決める。

| 保存先 | 保存するもの・責務 |
| --- | --- |
| `discord_notifications` | 通知 ID、用途・種別、dedupe key、payload とそのバージョン・照合情報、受付日時、配送状態、claim token・期限、試行数・次回時刻・最終エラー、終端・整理日時 |
| `discord_notification_parts` | 通知内の部分番号と順序、renderer バージョン、送信開始・結果、Discord message ID。受付 payload から再現できる本文を二重に永続化しない |
| アンケート用関連テーブル | Session 参照、aggregate revision・ordinal、書戻し先など。Session 内の順序・後続取消・回復と業務完了に使用 |
| A/B 用関連テーブル | 通知種別、元の論理ジョブ ID、業務成功時刻、成功時に取得した設定世代。`種別 + 元ジョブ ID` を一意にする |
| `discord_notification_settings` | A/B 別の ON/OFF と世代。初期値は両方 ON。アンケートには適用しない |
| `discord_notification_targets` | A の対象下書き、B に掲載した試合との対応。確定・削除と受付・配送の競合を扱うための識別情報 |

共通化するのは、通知の識別、配送順序の実行、claim、再試行、結果記録、保持期間の処理である。アンケートの Session 順序・最新状態からの表示・開催確定と、A/B の固定表示・設定世代・取消条件は、用途ごとの型と処理に閉じ込める。用途と関連行の組合せが不正な通知を作れないよう、制約または DB 操作境界で保証する。終端・整理済み通知は最小記録だけで成立する形を定義し、アンケートの Session 整理で通知本体の重複防止記録が消えないようにする。

通知本体は受付記録と配送待ち記録を兼ねる。A/B の元ジョブ・分析成果物・業務対象の削除に、通知本体・固定 payload・重複防止記録を連鎖削除させない。本文整理時にも元ジョブの一意性と内容照合情報を維持し、再受付から同じ通知を再生成しない。

**A/B の契約**

- A は画像ごとの OCR 成功・要確認ジョブを単位とする。B は公開・再利用に成功した論理分析ジョブを単位とする。実行 attempt は別通知にしない。手動の新規分析ジョブは別の単位となる。
- 通知 ID は種別と元ジョブ ID から安定して決める。`schemaVersion` を変えても通知 ID やジョブ単位の一意性は変わらない。文字列表現、payload の正規化・照合方式、そのバージョンを consumer 契約に定義する。
- Worker は業務成功の確定時に A/B の設定・世代を取得し、成功 commit 後に一度だけ HTTP 送出する。送信時点の設定で成功時点を代用しない。業務処理を通知の失敗で巻き戻さない。
- producer 側の通知 outbox、HTTP 再試行・欠落回収、API による代理送出は追加しない。Summit 受付前の欠落は許容する。
- Summit は通知 ID・固定 payload・関連情報・配送待ちまたは取消状態を一つの transaction で保存し、その commit を受付完了とする。新規は `202`、同じ内容の既存通知・取消済み通知は `200`、同じ識別で内容が異なるものは `409` とする。2xx は Discord への配送完了を意味しない。
- commit 後に HTTP 応答を失っても保存済み行から回収できる。二重受付・並行受付は同じ行へ収束する。未対応バージョンや不正 payload は保存前に拒否する。
- B は公開時点の対象試合、全 4 人の順位、作品通算・シーズン通算の前後値・対象数・差分、対象試合ごとの銀次、メモ全文、表示名・文脈・リンクを固定する。作品通算・シーズン通算は全マップを含む。後日の編集や成果物整理で再計算しない。
- B の初回、対象 0 件、比較不能、微小差分を区別する。再利用は同じ現在値を前後に使用する。メタデータ更新だけでは新しい分析通知を作らない。payload v1 の型・例と、保持中の v1 を読み続ける方針を文書化する。
- A は対象下書きの確定・削除で未開始部分を取り消す。B は掲載試合の一つでも削除されたら、その通知の未開始部分をすべて取り消す。残存試合だけで内容を作り直さない。元ジョブや成果物の履歴整理だけでは取消としない。

**競合・状態遷移の設計**

既存の `PENDING` / `IN_FLIGHT` / `DELIVERED` / `FAILED` / `CANCELLED` を基礎に、共通状態、用途ごとの遷移可否、取消理由、部分配送状態を定義する。claim 取得と Discord 送信開始は別の操作とする。

| DB 操作 | 保証すること |
| --- | --- |
| 業務成功時の設定取得 | 成功確定と設定世代の取得を一つの境界として扱い、OFF と競合してもどの世代かが確定する |
| 受付 | 同じ ID / 元ジョブの競合を一意制約で収束させ、設定世代と業務対象の現在状態を検査して pending または cancelled を保存する |
| 設定変更 | OFF の確定、世代の更新、該当する未開始部分の取消を一つの transaction で行う。再 ON 後の遅延受付も旧世代なら取消となる |
| 下書き確定・対象削除 | 業務変更と取消を同じ transaction で成立させる。受付・送信開始と共通のロック規約を使い、対象確認後の削除を見逃さない |
| claim | 期限・一意 token を発行し、同じ通知を同時所有させない。アンケートの前後関係と、各通知内の部分順序を守る |
| 部分の送信開始 | HTTP 直前に短い transaction で所有権・期限・設定世代・取消・対象状態を再確認し、当該部分の開始を記録する |
| 結果確定 | token による比較更新で古い所有者からの確定を拒否する。message ID を部分ごとに記録し、配送済み部分を再送しない |
| 再試行・回復 | 期限切れ claim を回収し、次回実行時刻と有限の試行上限を守る。アンケート固有の chain 復帰を A/B に適用しない |
| 整理 | 保持期間を過ぎ、処理が終わった通知の本文・配送詳細を整理する。一意性・照合情報・終端記録は保持する |

DB transaction を Discord HTTP の間は保持しない。送信開始が先に確定した部分は、後続の OFF・削除後に届く場合がある。取消は残りの送信を禁止しつつ、開始済み部分の結果を正当な token で記録できるようにする。親通知は `CANCELLED` と部分配送の記録を保持し、再 ON や通常の回復で続送しない。

Discord 側の成功応答を失った場合など、外部配送の成否が不明な区間での重複は許容する。DB 上の所有権と配送済み記録による重複抑止を保証し、外部副作用の exactly-once は要件にしない。

実装では既存の下書き確定・削除、試合削除、分析ジョブ整理の transaction を確認し、すべての競合経路で同じロック順序を使う。直接 SQL を含む既存経路で抜けが生じないよう、必要な関数・trigger を custom migration として提供する。新規の常時 DB ポーリングは追加せず、保存後の起動通知と既存の低頻度 supervisor による回収へ接続する。

**実施順序**

1. **開始点と変更範囲を確定する。** 最新 master、ローカル commit、適用済み migration と hash、Summit と momo-result の利用 DB 参照を再確認する。調査時点でローカルの migration 末尾と共有・本番の末尾に差があったため、既存 commit を失わず最新履歴に揃えてから追加する。採番は実装時の末尾に従い、適用済みファイルは変更しない。

2. **consumer 契約と移行対応表を作る。** ID・payload v1・内容照合・状態遷移・DB 操作・ロック順序・エラー理由を文書化する。既存 outbox の各列が共通通知、部分配送、アンケート用関連のどこへ移るかを定義し、ID・dedupe key・payload・状態・message ID・順序を保持する。新規の A/B HTTP 受付・描画と、今回必要な既存アンケート改修を分けて管理する。

3. **履歴保護と通知基盤の migration を作る。** `held_events.session_id` の削除動作を先に変更する。共通構造を schema migration で作り、別の custom migration で precondition・移行・初期設定・DB 関数・trigger を追加する。既存 outbox の移行検証後、不要な旧 shape を後段の schema migration で整理する。改名だけで安全に移せる箇所は改名を使用し、生成される drop/create を必ずレビューする。各段階の schema と snapshot を一致させる。

4. **終了済み Session の整理を移行手順に組み込む。** 対象を直前の状態から限定し、開催への削除依存が解消されていることを確認してから Session・回答と不要なアンケート用関連を整理する。開催履歴との対応が不明な過去 Session も例外保全しない。開催・参加者・試合等の保全比較に失敗した場合は切替を止める。進行中 Session や未配送通知は新構造で動かせる形を維持する。

5. **既存 Summit を同時に対応させる。** enqueue、claim、配送・message ID 書戻し、Session 内の順序、後続取消、再試行・起動回復、整理を共通テーブルへ移す。アンケート表示とリマインド後の Session 完了・開催履歴・参加者作成を維持する。この改修は DB 再構成の必須 companion とし、新しい A/B 機能の MOM-18 を待って旧 consumer の対応を先送りしない。

6. **実 DB と consumer で検証する。** 下記の受け入れ確認に加え、`pnpm build`、`pnpm db:check`、空の disposable DB への全 migration 適用、代表的な既存 DB の復元 copy への tail 適用を行う。Summit の `pnpm run ci`・`pnpm test:integration`、影響する momo-result API の DB 検証と Rust worker の DB 制御検証を実行する。接続先を隔離し、実 Discord 送信を伴わない検証を基本とする。

7. **停止切替の規範と手順を整える。** 今回承認されたメンテナンス方式を `docs/development.md` 第 6 節へ反映し、全 consumer を止めた切替の条件と順序を明記する。適用済み履歴の不変性、復元確認、protected environment による本番承認・preflight は維持する。対応 DB / consumer commit、適用順、確認方法、復旧手順を同じ切替単位として揃える。

8. **後続 Issue へ引き渡す。** MOM-15 は設定 API/UI と取消操作への接続、MOM-16 は OCR 通知と共通の一度だけの HTTP client、MOM-17 は分析公開時の固定 snapshot、MOM-18 は HTTP 受付・A/B 描画・配送回復を担当する。共通化に必要な既存 Summit 改修は MOM-14 の完了条件に含める。通知全体の結合・受入は MOM-19 に接続する。

**受け入れ確認**

| 観点 | 必須確認 |
| --- | --- |
| 履歴保全 | 開催 ID・開催日・開始日時・参加者、試合と子レコード・メモ・参照先を件数と値の両方で前後比較する。Session 整理に伴う `session_id` の NULL 化だけを意図した差分として扱う |
| 過去 Session 整理 | 開催リンクの有無にかかわらず、終了済み Session・回答の整理で既存開催・参加者・試合が消えない。未完了の Session は整理対象にならない |
| 新しい開催 | アンケート作成からリマインド配送後の開催・参加者記録まで成立する。Session 完了だけが先に残らず、再実行で履歴が重複しない |
| 原子的な受付 | 二重・同時受付、異内容の競合、途中 rollback、commit 後の応答喪失でも、固定内容と状態が一つの通知に収束する |
| 一意性と固定内容 | 元ジョブや成果物の整理、payload バージョン変更、本文保持期間の終了を経ても、同じ論理ジョブが新しい通知にならない |
| OFF と再 ON | 業務成功・受付・claim・部分送信開始それぞれとの競合で、旧世代の未開始部分が送られず、遅延受付や再 ON で復活しない |
| 対象の変更 | A の下書き確定・削除と B の掲載試合削除が、並行受付・送信開始と競合しても未開始部分を取り消す。単なるジョブ整理では取り消さない |
| claim と回復 | 同時 claim、期限切れ、旧 token の確定、再試行上限、再起動を実 transaction で確認する |
| 分割配送 | 順序を守り、既配送部分の message ID を維持する。途中失敗と途中 OFF・削除で、再送・続送の可否が合意どおりになる |
| 用途の分離 | A/B の OFF がアンケートに影響せず、アンケートの起動回復が A/B の FAILED / CANCELLED を無条件に復帰させない |
| migration 品質 | SQL と metadata、既存データ、constraint・index・function・trigger、ロック時間、固定したロック順序、`search_path`、identifier 長を確認する |

**メンテナンス当日の切替**

1. 対応版と検証結果を揃え、利用者へメンテナンスを通知する。API、Worker、Summit、scheduler・batch を含む全 writer と配送を停止する。
2. 復元可能な backup を取得し、復元 copy を読み出せることを確認する。最新の migration 履歴、Session と outbox の状態、保全対象の ID・値・参照を基準として記録する。secret や接続 URL の実値を記録しない。
3. protected な本番 migration 経路で、preflight と forward migration を適用する。履歴保護、通知構造の移行、終了済み Session 整理、旧 shape 整理の依存順を守る。
4. 全 consumer を対応版に揃え、保全対象の前後比較と既存機能の確認を行う。確認できるまで利用者からの書込みと外部配送を再開しない。
5. 既存アンケートと通常の記録機能を再開する。A/B は設定側と Summit 受付・配送側の準備が整った後に、Worker からの送出を有効にする。

新規書込みを受け入れる前に切替を戻す場合は、停止状態を維持して backup と旧 consumer を整合する組合せへ戻す。再開後の修復は、新規データを守る forward fix を原則とする。migration 履歴だけの巻戻しや保存 volume の削除は行わない。

MOM-14 の完了は、共有 DB 契約、移行成果物、既存 Summit の対応、必須 DB / consumer 検証、停止切替手順、後続 Issue への引渡しが揃った時点とする。複数 PR に分かれる場合、追加の必須作業が残る PR は `Refs MOM-14`、必要な companion を含めて merge で完了する最終 PR は `Fixes MOM-14` とする。

現時点でユーザー判断待ちの事項はない。過去の開催状況が確定しないことは、今回の実装・移行を妨げる条件にしない。
